# 작업 지시서 v2.0
### 방 단위 탐험 성장 RPG — 수직 슬라이스 (2개월)

- 기준 문서: 기획서 v0.3 / 밸런스시트 v0.1
- 전제: mLua 문법은 학습하지 않는다. **판단 기준만 갖고 AI에게 지시한다.**

---

## 0. 사용법

### 0.1 역할 고정
| 주체 | 역할 |
|---|---|
| **Claude Code / 코드 AI** | 코드 생성·수정·커밋 (로컬 파일 직접 접근) |
| **웹 채팅 Claude** | 설계 판단, 코드 검증, 방향 상담 (붙여넣기로) |
| **단풍 (에디터 내)** | mLua API 실존 확인, 에디터 특유 동작 |
| **본인** | 실행·판정·결정 |

### 0.2 모든 프롬프트에 붙일 공통 규칙 (★중요)
> 아래 블록을 각 태스크 프롬프트 **끝에 항상 복사해 붙일 것.**
> 이것이 "학습 대신 지시서에 판단 기준을 내장한다"의 실체다.

```
[공통 규칙 — 반드시 지킬 것]
1. 실행공간을 코드 상단 주석에 명시할 것 (-- @서버 / -- @클라이언트).
2. 다음은 반드시 서버에서 실행: 데미지 계산, 스탯 분배, 경험치/레벨,
   포획 판정, 환생 처리, 데이터 저장. 클라이언트는 입력과 연출만.
3. 수치를 코드에 하드코딩하지 말 것. 데이터 테이블 또는 상수 모듈에서 읽을 것.
4. 존재하지 않는 API를 추측해서 쓰지 말 것. 확실하지 않으면 "확인 필요"로 표시하고
   대안을 제시할 것.
5. 영구 데이터(스킬 컬렉션·랜드마크·환생 횟수)와 회차 데이터(레벨·스탯 분배)는
   저장 구조에서 분리할 것.
6. 코드를 준 뒤, 내가 직접 확인해야 할 것을 3줄 이내로 알려줄 것.
```

### 0.3 작업 사이클
```
프롬프트 실행 → 에디터에서 직접 실행 → ✅ 완료조건 통과 → 커밋 → 다음
                                    ↓ 실패
                        에러+코드+의도를 웹 채팅 Claude에 검증 요청
```
**한 문제에 2시간 이상 막히면 멈추고 검증 요청.**

### T1. 방 단위 이동 (3~4일) ★이 게임의 원자 단위

```
탑다운 게임의 '방 단위 이동'을 구현해줘.

요구사항:
- 캐릭터가 상하좌우(8방향)로 이동. 중력/점프 없음.
- 화면 하나 = 하나의 방. 카메라 고정(스크롤 추적 없음).
- 방 가장자리에 도달하면 RoomTable.connections에 따라 다음 방으로 전환.
- 전환 시 캐릭터는 반대편 가장자리에서 등장.
- 모바일 가상 조이스틱 입력 기준.
- 스프라이트는 좌우 플립만 사용 (상하 이동 시 애니메이션 없음).

질문:
1. 메월드 기본 이동 컴포넌트는 횡스크롤 전제인데, 탑다운으로 쓰려면
   어떤 설정이 필요한가? (중력 비활성화 포함)
2. 방 전환을 '맵 로드'로 할지 '엔티티 재배치'로 할지 — 각 방식의 장단점

[공통 규칙 붙이기]
```
✅ **완료** (2026-08-04, PR #1 머지): 방 5개를 포탈로 오갈 수 있다.
- 맵 5개(`map01`~`map05`, 전부 RectTile) + 포탈 8개. 목적지는 `RoomTable`이 소유
- 카메라·플레이어를 방 경계 안에 가둠 (`RoomCamera`) — 4개 구석 실측 검증
- 이동속도 `InputSpeed 1.8` (실효 1.50 u/s), 점프 비활성
- 좌우 플립은 엔진 기본 동작으로 충족. 상하 이동 걷기 애니메이션은 `PlayerTopDownAnim`으로 보정
- ⬜ **모바일 테스트는 아직 안 했다** (PC 에디터에서만 검증)
⚠️ **함정**: 기본 무브먼트가 플랫포머 전제일 가능성. 중력 비활성이 첫 관문.

**착수 전 확인된 사실 (2026-08-04)**
- T1의 첫 관문은 "중력 비활성"이 **아니라 맵 모드 선택**이다. 현재 워크스페이스에 로드된
  `TileMapTemplate`은 `TileMapMode = 0`(MapleTile, 횡스크롤)이라 **상하 이동이 물리적으로 불가능**하다.
  스크립트로 못 고친다 — 모드가 Body·중력·충돌 스택 전체를 결정한다.
- 탑다운은 **`TileMapMode = 1` (RectTile) + `KinematicbodyComponent`** 조합이며,
  이 모드는 중력이 없어 "중력 비활성" 작업 자체가 불필요하다.
- 진행 방향: `MapBuilder.fromTemplate(templatePath("rect"), "map01")`로 **새 RectTile 맵을 만든다.**
  기존 맵의 모드를 바꾸는 방식은 지형이 전부 리셋되고 Maker에서 직접 우클릭해야 하므로 쓰지 않는다.
  `map01`로 만들면 `SectorConfig`의 기존 `map://map01` 참조도 함께 유효해진다.
- 스프라이트는 **좌우 플립만** 사용 — 상하 이동 시 마지막 좌우 방향을 유지한다 (에셋에 상하 프레임 없음).

**질문 2번(방 전환 방식) 결정: 방 1개 = 맵 1개 + `PortalComponent`** (2026-08-04 승인)
- MSW 네이티브 포탈로 맵 간 이동. 공식 문서에 *"Two-Way Portal between Maps"* 로 명시되어 있다.
- 방 5개 ↔ `map01`~`map05`. 연결은 `RoomTable.map_name` 컬럼으로 데이터가 소유한다.
- **포탈은 단방향이다** — "Only one destination can be set per component and the portal is one-way only".
  양방향 통로 1개 = 양쪽 맵에 포탈 1개씩, 서로의 `PortalEntityRef`를 가리키게 한다.
  연결 8개 → 포탈 엔티티 16개.
- `PortalEntityRef`는 **EntityRef**라 맵 전환에도 참조가 살아남는다. UUID는 AI가 직접 주입한다.
- ⚠️ **미확인**: 포탈 발동이 자동(범위 진입)인지 키 입력인지. 문서에 *"when performing a specific
  action (such as a key input) within the portal area"* 라고 되어 있어 지시서의 "가장자리 도달 시
  전환"과 다를 수 있다. **T1-2에서 실측 후 확정** — 키 입력이면 `TriggerComponent` 자동 전환으로
  대체할지 결정 필요.
- 채택하지 않은 대안: 한 맵에 방을 격자로 배치(카메라 바운드 방식) / 런타임 타일 교체.
  전자는 로딩이 없다는 장점이 있었으나, 포탈이 T6 "잠긴 문을 보여준다" 연출과 직결되어 포탈 방식을 택함.

**진행 상황**: T1-1 완료 — `map01`~`map05` 생성(전부 RectTile), `SectorConfig` 등록,
`RoomTable.map_name` 연결. 남은 것: T1-2 포탈 배치·연결 / T1-3 카메라 고정 + 좌우 플립.

## Phase 2 — 게임 성립 (5~7주)

### T5. 포획 + 스킬 획득/장착 (4~5일)

```
포획 시스템과 스킬 장착을 구현해줘.

- 처치 시 자동 판정. 확률 = 3% + LUK × 0.1%p
- 종별 40킬 천장 (누적 40마리째는 확정 포획)
- 성공 시 MonsterTable.drop_skill_id를 컬렉션에 추가. 중복 시 강화 카운트 +1
- 컬렉션은 환생해도 유지되는 영구 데이터

슬롯 구조 (중요):
- **직업 스킬 슬롯**: 고정. 직업 선택 시 자동 장착되어 항상 사용 가능.
  몬스터 슬롯과 완전히 별개이며, 몬스터 슬롯을 잠식하지 않는다.
- **몬스터 스킬 슬롯**: **시작 1개.** 확장 조건은 ①보스 클리어 ②환생 횟수 (T6/T7에서 구현)
- 따라서 게임 시작 시점의 동시 사용 액티브 = 직업 스킬 + 몬스터 1 = 최소 2개
- 몬스터 슬롯 상한은 3

요청:
1. 종별 킬 카운트·천장을 포함한 판정 로직
2. 포획 성공 연출 흐름
3. 스킬 장착 데이터 구조 + 버튼 바인딩
   (직업 슬롯과 몬스터 슬롯을 분리하되, 사용 인터페이스는 통일)
4. 몬스터 슬롯 수를 데이터로 관리 — 나중에 보스/환생으로 증가시킬 수 있는 구조
5. 영구/회차 데이터 저장 분리

[공통 규칙 붙이기]
```
✅ **완료**: LUK 빌드에서 체감 차이가 난다(시트: 9마리 vs 33마리). 획득 스킬로 공격 가능.

### T6. 게이트 시스템 (3~4일) ★코어 재미의 심장

```
'잠긴 문' 게이트 시스템을 구현해줘. 이 게임의 핵심 재미다.

게이트 3종 (RoomTable.gate_condition으로 정의):
1. 수치 게이트: ATK 또는 레벨이 X 이상이어야 통과
2. 열쇠 게이트: 특정 스킬(is_key_skill=true) 보유 시 통과
3. 환생 게이트: unlocked_areas에 해당 구역이 있어야 통과

UX 요구사항:
- 잠긴 문은 **보여야 한다**. 조건 미달 시 "무엇이 부족한지" 명확히 표시
  (예: "공격력 50 필요 — 현재 32")
- 조건 충족 시 시각적으로 열린 상태로 변경

보스 처치 보상 (이 태스크에 포함):
- 보스방의 보스를 처치하면 **몬스터 스킬 슬롯 +1** (1 → 2)
- 보스 클리어 기록은 영구 데이터. 환생해도 유지되며 중복 지급 안 됨.
- 처치 시 "슬롯이 늘었다"를 명확한 연출로 알릴 것 — 성취가 보여야 한다.

요청:
1. 게이트 조건 판정 로직 (데이터 기반, 새 게이트 추가가 데이터만으로 가능하게)
2. 조건 미달/충족 UI 표현
3. 방 전환(T1)과의 연동
4. 보스 처치 → 슬롯 확장 처리 (영구 데이터, 중복 방지)

[공통 규칙 붙이기]
```
✅ **완료**: 처음엔 못 가던 방을, 레벨을 올린 뒤 통과할 수 있다.
✅ **완료**: 보스를 잡으면 몬스터 슬롯이 2개가 되고, 스킬 2개를 동시에 장착할 수 있다.
📌 **이 순간이 게임의 코어다.** 여기서 "오, 열렸다"가 안 느껴지면 연출·조건 표시를 손볼 것.

### T7. 환생 + 랜드마크 (3~4일)

```
환생 시스템을 구현해줘.

리셋: level, exp, stats, (회차 장비)
유지: owned_skills, rebirth_count, highest_level, landmark_claimed, unlocked_areas

랜드마크 규칙:
- 도달 레벨 기준. 그 레벨에서 **환생해야** 보상 획득 (도달만으로는 미지급)
- 슬라이스 사다리: **Lv30 환생 → 직업2 해금 + 몬스터 슬롯 +1(2→3) + 신규 구역 개방**
  (기획서 §4.5 "한 랜드마크에 한 축만"의 **슬라이스 한정 예외** — 2026-08-04 승인.
   본편 사다리는 밸런스시트 기준. LandmarkTable은 교체 가능한 데이터 구조로 만들 것)
- 캡 도달 전부터 "다음 환생 시: OO" 문패 UI로 사전 노출

슬롯 확장 2축 (T6과 함께 완성):
- 보스 클리어(공간 축) = T6에서 1→2
- 환생 횟수(회차 축) = 여기서 2→3
- 두 축이 각각 독립적으로 작동해야 하며, 슬롯 수는 영구 데이터로 관리

요청:
1. 환생 트랜잭션 — 중간에 앱이 죽어도 반쪽 상태가 남지 않도록 원자적 처리
2. 환생 확인 화면: 잃는 것 / 얻는 것 / 직업 선택을 한 화면에 (모바일)
   — 직업 선택 시 각 직업의 고유 스킬을 미리 보여줄 것 (선택의 근거)
3. unlocked_areas가 게이트(T6)와 연동되는 구조
4. 환생 횟수에 따른 슬롯 확장 (T6의 보스 축과 중복 계산되지 않도록)

[공통 규칙 붙이기]
```
✅ **완료**: 환생 후 Lv1 시작 + 컬렉션 유지 + 새 구역이 열린다. 강제 종료 테스트 통과.
✅ **완료**: 환생 후 몬스터 슬롯 3개. 두 확장 축이 모두 작동함을 확인.

[공통 규칙 붙이기]

## Phase 3 — 통합 검증 (8주)

### T9. 플레이 검증

- [ ] 새 계정으로 처음부터 끝까지 플레이
- [ ] **게이트 통과 순간의 쾌감** — 이게 핵심 판정
- [ ] 세션 단위 확인: 15분에 의미 있는 진전(레벨/포획/문 하나)이 있는가
- [ ] 빌드 3종(공격형/균형형/LUK형) 각 1회차 — 체감이 다른가
- [ ] **슬롯 확장의 체감** — 1→2, 2→3이 될 때 "이제 조합이 된다"는 감각이 오는가
- [ ] **직업 선택의 이유** — 직업 고유 스킬이 실제로 플레이 스타일을 다르게 만드는가
- [ ] 방 단조로움 점검 — 사냥방이 연속되는 구간이 없는가
- [ ] 실측을 시트에 역기입 → 밸런스시트 v0.2

### 최종 검증 질문
> **잠겨 있던 문이 내 성장으로 열리는 순간, 그 앞의 그라인딩이 보상으로 느껴지는가?**

- **'예'** → 확장 단계로. 방 추가, 직업 추가, 컬렉션 패시브 구현
- **'아니오'** → 게이트 배치 간격, 조건 표시 UX, 성장 템포부터 재설계.
  **콘텐츠를 더 넣지 말 것.**
