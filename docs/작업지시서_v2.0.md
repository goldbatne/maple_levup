# 작업 지시서 v2.0
### 방 단위 탐험 성장 RPG — 수직 슬라이스 (2개월)

- 기준 문서: 기획서 v0.3 / 밸런스시트 v0.1
- 전제: mLua 문법은 학습하지 않는다. **판단 기준만 갖고 AI에게 지시한다.**

## 0. 사용법

### 0.1 역할 고정
| 주체 | 역할 |
|---|---|
| **Claude Code / 코드 AI** | 코드 생성·수정·커밋 (로컬 파일 직접 접근) |
| **웹 채팅 Claude** | 설계 판단, 코드 검증, 방향 상담 (붙여넣기로) |
| **단풍 (에디터 내)** | mLua API 실존 확인, 에디터 특유 동작 |
| **본인** | 실행·판정·결정 |

### 0.2 모든 프롬프트에 붙일 공통 규칙 (★중요)
> 아래 블록을 각 태스크 프롬프트 **끝에 항상 복사해 붙일 것.**
> 이것이 "학습 대신 지시서에 판단 기준을 내장한다"의 실체다.

```
[공통 규칙 — 반드시 지킬 것]
1. 실행공간을 코드 상단 주석에 명시할 것 (-- @서버 / -- @클라이언트).
2. 다음은 반드시 서버에서 실행: 데미지 계산, 스탯 분배, 경험치/레벨,
   포획 판정, 환생 처리, 데이터 저장. 클라이언트는 입력과 연출만.
3. 수치를 코드에 하드코딩하지 말 것. 데이터 테이블 또는 상수 모듈에서 읽을 것.
4. 존재하지 않는 API를 추측해서 쓰지 말 것. 확실하지 않으면 "확인 필요"로 표시하고
   대안을 제시할 것.
5. 영구 데이터(스킬 컬렉션·랜드마크·환생 횟수)와 회차 데이터(레벨·스탯 분배)는
   저장 구조에서 분리할 것.
6. 코드를 준 뒤, 내가 직접 확인해야 할 것을 3줄 이내로 알려줄 것.
```

### 0.3 작업 사이클
```
프롬프트 실행 → 에디터에서 직접 실행 → ✅ 완료조건 통과 → 커밋 → 다음
                                    ↓ 실패
                        에러+코드+의도를 웹 채팅 Claude에 검증 요청
```
**한 문제에 2시간 이상 막히면 멈추고 검증 요청.**

### T1. 방 단위 이동 (3~4일) ★이 게임의 원자 단위

```
탑다운 게임의 '방 단위 이동'을 구현해줘.

요구사항:
- 캐릭터가 상하좌우(8방향)로 이동. 중력/점프 없음.
- 화면 하나 = 하나의 방. 카메라 고정(스크롤 추적 없음).
- 방 가장자리에 도달하면 RoomTable.connections에 따라 다음 방으로 전환.
- 전환 시 캐릭터는 반대편 가장자리에서 등장.
- 모바일 가상 조이스틱 입력 기준.
- 스프라이트는 좌우 플립만 사용 (상하 이동 시 애니메이션 없음).

질문:
1. 메월드 기본 이동 컴포넌트는 횡스크롤 전제인데, 탑다운으로 쓰려면
   어떤 설정이 필요한가? (중력 비활성화 포함)
2. 방 전환을 '맵 로드'로 할지 '엔티티 재배치'로 할지 — 각 방식의 장단점

[공통 규칙 붙이기]
```
✅ **완료** (2026-08-04, PR #1 머지): 방 5개를 포탈로 오갈 수 있다.
- 맵 5개(`map01`~`map05`, 전부 RectTile) + 포탈 8개. 목적지는 `RoomTable`이 소유
- 카메라·플레이어를 방 경계 안에 가둠 (`RoomCamera`) — 4개 구석 실측 검증
- 이동속도 `InputSpeed 1.8` (실효 1.50 u/s), 점프 비활성
- 좌우 플립은 엔진 기본 동작으로 충족. 상하 이동 걷기 애니메이션은 `PlayerTopDownAnim`으로 보정
- ⬜ **모바일 테스트는 아직 안 했다** (PC 에디터에서만 검증)
⚠️ **함정**: 기본 무브먼트가 플랫포머 전제일 가능성. 중력 비활성이 첫 관문.

**착수 전 확인된 사실 (2026-08-04)**
- T1의 첫 관문은 "중력 비활성"이 **아니라 맵 모드 선택**이다. 현재 워크스페이스에 로드된
  `TileMapTemplate`은 `TileMapMode = 0`(MapleTile, 횡스크롤)이라 **상하 이동이 물리적으로 불가능**하다.
  스크립트로 못 고친다 — 모드가 Body·중력·충돌 스택 전체를 결정한다.
- 탑다운은 **`TileMapMode = 1` (RectTile) + `KinematicbodyComponent`** 조합이며,
  이 모드는 중력이 없어 "중력 비활성" 작업 자체가 불필요하다.
- 진행 방향: `MapBuilder.fromTemplate(templatePath("rect"), "map01")`로 **새 RectTile 맵을 만든다.**
  기존 맵의 모드를 바꾸는 방식은 지형이 전부 리셋되고 Maker에서 직접 우클릭해야 하므로 쓰지 않는다.
  `map01`로 만들면 `SectorConfig`의 기존 `map://map01` 참조도 함께 유효해진다.
- 스프라이트는 **좌우 플립만** 사용 — 상하 이동 시 마지막 좌우 방향을 유지한다 (에셋에 상하 프레임 없음).

**질문 2번(방 전환 방식) 결정: 방 1개 = 맵 1개 + `PortalComponent`** (2026-08-04 승인)
- MSW 네이티브 포탈로 맵 간 이동. 공식 문서에 *"Two-Way Portal between Maps"* 로 명시되어 있다.
- 방 5개 ↔ `map01`~`map05`. 연결은 `RoomTable.map_name` 컬럼으로 데이터가 소유한다.
- **포탈은 단방향이다** — "Only one destination can be set per component and the portal is one-way only".
  양방향 통로 1개 = 양쪽 맵에 포탈 1개씩, 서로의 `PortalEntityRef`를 가리키게 한다.
  연결 8개 → 포탈 엔티티 16개.
- `PortalEntityRef`는 **EntityRef**라 맵 전환에도 참조가 살아남는다. UUID는 AI가 직접 주입한다.
- ⚠️ **미확인**: 포탈 발동이 자동(범위 진입)인지 키 입력인지. 문서에 *"when performing a specific
  action (such as a key input) within the portal area"* 라고 되어 있어 지시서의 "가장자리 도달 시
  전환"과 다를 수 있다. **T1-2에서 실측 후 확정** — 키 입력이면 `TriggerComponent` 자동 전환으로
  대체할지 결정 필요.
- 채택하지 않은 대안: 한 맵에 방을 격자로 배치(카메라 바운드 방식) / 런타임 타일 교체.
  전자는 로딩이 없다는 장점이 있었으나, 포탈이 T6 "잠긴 문을 보여준다" 연출과 직결되어 포탈 방식을 택함.

**실측 결과 (T1-2, 2026-08-04)**: 위 "미확인" 항목의 결론 — **`PortalComponent`를 쓰지 않았다.**
`PortalEntityRef`는 맵을 넘는 참조를 유지하지 못했고(런타임 nil + `LWA-3019`), Maker가 저장 시
값을 null로 지워버렸다. 대신 **`TriggerComponent` + `_TeleportService:TeleportToMapPosition`**으로
전환했고, 목적지는 `RoomTable`이 소유한다. 전환은 범위 진입 시 자동이다.
`TriggerComponent.BoxSize`는 기본값이 (0,0)이라 반드시 명시해야 한다(3×3 사용).

### T3. 전투 + 데미지 공식 (4~5일)

```
전투 코어를 구현해줘.

데미지 공식: 스킬계수 × ATK² / (ATK + 몬스터DEF)   [기준 계수 1.2]
몬스터 수치: Lv1 HP 30, DEF 5, EXP 5
            성장 공비 HP×1.09, DEF×1.08, EXP×1.10 (레벨당)
목표: 처치당 약 10초 (이동 포함)

- 기본 공격은 자동(근접 범위 판정), 액티브 스킬은 버튼 탭(2~3개 상한).
- 몬스터 AI는 슬라이스에선 '제자리 + 피격 반응'까지만.
- 몬스터는 방(RoomTable)에 속하며, 방 진입 시 스폰.

요청:
1. 공격 판정 → 데미지 계산 → HP 차감 → 사망 → EXP 지급의 이벤트 흐름
2. 데미지 숫자 표시(클라 연출)와 서버 판정의 분리
3. 방 단위 스폰/리스폰 처리

[공통 규칙 붙이기]
```
✅ **완료** (2026-08-05, PR #4 + T3-4/T3-5): Lv1 몬스터를 기준 빌드로 **정확히 4타에 처치**.
ATK 10 vs DEF 5 → 1.2 × 10² / 15 = 8, HP 30 → 4타. 시트 예측과 실측 일치.
⚠️ **함정**: 데미지 계산을 클라에서 하면 이후 전부 재작업.

**구현 메모**
- 공식은 `CombatFormula`(@Logic) 한 곳에만 둔다. 호출은 서버 스크립트만 한다.
  클라이언트는 `HitEvent` 결과로 숫자를 띄우기만 한다(요청 2의 분리).
- 데미지 숫자 자동 표시는 **방어자에 `DamageSkinSpawnerComponent` + `DamageSkinComponent`
  둘 다** 필요하다. Spawner만 있으면 아무 에러 없이 숫자가 안 뜬다 — 실측으로 확인.
- 몬스터 `HitComponent.CollisionGroup`은 `Monster`여야 한다. 공격 측이
  `CollisionGroups.Monster`로 필터하므로, 값이 다르면 **에러 없이 0마리가 맞는다.**
- 기본 공격은 **플레이어 중심 원형 판정**이다. 탑다운이라 방향 박스로는
  위/아래 몬스터가 맞지 않는다. 반경·주기는 `GameBalance`의 구현 상수
  (`player_attack_range` / `player_attack_interval`) — 밸런스시트에는 없는 값이다.
- 리스폰은 개체가 아니라 **방 단위**로 센다. `RoomSpawner`가 살아있는 수를 세어
  `RoomTable.monster_count`만큼 채운다. 개체별 리스폰이면 방 정원이 데이터가 아니라
  개체 설정에 흩어진다.
- 몬스터 데이터 id(`m_slime`)와 모델 id(`slime`)는 `MonsterTable.model_id`가 잇는다.
  이름 규칙으로 엮지 않는다.

T3-1부터 PR #4·#5·#6에 걸쳐 *"처치 타수가 Lv1 4타 → Lv10 2타로 오히려 줄어들어
시트 목표와 어긋날 수 있다"* 고 반복 보고했으나, **시트가 이미 그 형태를 예측하고 있었다.**

시트 '처치 타수' 컬럼은 **V자**다: `4 → 3 → 2(Lv10 최저) → 3 → 4 → 5(Lv30)`.
필자가 곡선의 앞 절반만 보고 우려한 것이다. 뒤로 가면 몬스터 HP 공비(1.09)가
ATK 선형 성장을 따라잡아 다시 올라간다.

시트 자체 체크 지표가 **"처치 타수 흐름: Lv1 대비 캡에서 2배 이내 권장"** 인데
4타 → 5타 = **1.25배**로 권장 범위 안이다. **조절할 것이 없다.**

- ⚠ **`_HttpService:JSONEncode`는 중첩된 빈 테이블에서 죽는다.**
  `{Run={level=1}}` → OK, `{Run={level=1,eq={}}}` → `[LEA-3001] UnknownType`.
  최상위 빈 테이블은 조용히 빈 문자열을 돌려줘서 더 헷갈린다.
  → 구조체 `Serialize`가 빈 테이블 필드를 아예 빼도록 했다(`HasAny`).
- ⚠ **SyncTable에는 순회 API가 없다** (`.d.mlua` 정의 자체가 없음).
  저장할 때 "안에 뭐가 들었나"를 물어볼 수 없어, GameData가 아는 **키 공간 전체**를
  훑는다 (`GetAllSkillIds` / `GetAllMonsterIds` / `GetAllRoomIds` / `GetRebirthAreaIds`).
  부작용: CSV에서 지운 id는 다음 저장에서 함께 사라진다.
- ⚠ **컴포넌트 `OnBeginPlay` 순서는 정해져 있지 않다.** 로드가 채운 값을 나중에 도는
  초기화가 지운다. `PlayerStats.OnBeginPlay`의 `ResetRun()`을 제거하고,
  `PlayerSkillSlots`는 슬롯 수를 대입하는 대신 `RecomputeSlotCount()`로 유도하게 바꿨다.
- `BatchSet*`의 반환은 `List<string>`이라 파라미터를 `table`로 선언하면 LSP가 막는다 → `any`.
- 방 복원은 `OnBeginPlay` 0.5초 뒤에 한다. 즉시 텔레포트하면 출발/도착 맵이 엉킨다.
  도착점은 방 한가운데(0,0,0) — 포탈은 가장자리에 있어 트리거에 걸리지 않는다.

#### T8-2 구현 완료 — 로깅 5종 (2026-08-07)

`Progress/ProgressLog.mlua` (@Logic, 서버). 한 줄 규격으로 모은다:


`[PROGRESS]`만 걸러내면 세션 전체가 시간순으로 나온다. 파이프 + key=value.

| `rebirth` | 없음 — **T7이 부를 자리**. 형식이 갈라지지 않게 미리 만들어 뒀다 |

판단과 실측:
- **DataStorage에 쓰지 않는다.** 세이브가 아니라 관측 기록이다. 저장하면 Credit을 먹고
  보관·회전 규칙을 또 정해야 하는데, 필요한 건 "이번 판이 어땠나"뿐이라 콘솔로 충분하다.
- **타임스탬프를 `ToFormattedString`으로 만들지 않는다.** 포맷 문자열 규격이 틀리면
  예외가 나고 **모든 로그 호출이 죽는다**. `DateTime.UtcNow`의 Year/Month/… (문서화된
  int32 프로퍼티)를 직접 조립한다. 기록이 기록 때문에 게임을 멈추면 안 된다.
- ✔ `DateTime.UtcNow` **정적 프로퍼티 접근이 mlua에서 된다** (빌드·런타임 확인).
- ✔ **`UserLeaveEvent`는 Maker의 Play 종료에서도 뜬다.** T8-1의 퇴장 저장 경로가
  실제로 도는 것을 여기서 처음 확인했다.
- 세션 카운터는 `@Logic`에 userId별로 둔다. 맵을 옮겨도 이어져야 하고,
  나간 유저는 버려야 재접속 시 이전 세션 수치가 섞이지 않는다.

> "INT는 마법사 전용이라 1회차 무효"라고 적었는데 **틀렸다.**

버섯은 r_04에 있어 1회차에도 잡는다. **포획해서 끼우면 INT가 실제로 계수로 쓰인다.**
기획서 §4.1의 *"스탯 분배가 직업 스킬 vs 주력 몬스터 스킬의 선택이 된다"*가
데이터에 이미 들어가 있다.

**그런데 성립하지 않는다.** 주황 버섯(HP42 DEF6.8) 상대 4초 창(자동 4타 + 액티브 1회):

| 빌드 | 자동 공격 | 액티브 | 합계 |
|---|---:|---:|---:|
| ATK45 + 점액 튀기기(ATK) | 4×47 = 188 | 39 | **227** |
| ATK45 + 포자 살포(INT 0) | 4×47 = 188 | **1** | 189 |
| ATK10 / INT45 + 포자 살포 | 4×7 = 28 | 43 | **71** |
| ATK25 / INT25 + 포자 살포 | 4×24 = 96 | 22 | 118 |

**자동 공격이 총딜의 83%를 낸다**(188/227). 자동 공격은 `attackInfo=nil`이라 항상 ATK고
주기가 1초인데, 액티브는 쿨 4초다. 그래서 INT에 투자하면 총딜이 **1/3로 떨어진다.**
반대로 ATK 빌드가 포자 살포를 끼우면 **1 데미지** — 슬롯만 버린다.
→ **버섯 스킬은 지금 누구에게도 쓸모가 없다.** INT가 죽은 게 아니라,
**자동 공격이 ATK 고정인 구조가 INT 빌드를 불가능하게 만든다.**

**DEF는 미구현이다.** `GetTotalDef()`의 호출부가 **`RoomGate` 하나뿐**(grep 확인).
피격 경로에 없다 — `PlayerHit`(HitComponent)도 `MonsterAttack`(AttackComponent)도
`CalcDamage`를 오버라이드하지 않아 엔진 기본 데미지가 그대로 들어오고, 거기에
`PlayerStats`를 읽는 지점이 없다. 기획서 §4.7이 `DEF = 생존(통합 방어)`로 이미
정의했으므로 이건 **설계 공백이 아니라 구현 누락**이다.

즉 균형형이 넣는 5포인트 중 **1포인트(DEF)는 아무 데도 안 닿고**,
INT 1포인트는 닿기는 하나 총딜을 깎는다. 표의 "균형형 12.5분"은
자동 공격 기준이라 그대로 유효하다.

**④ 부작용 — 돌 정령 스킬이 수십 회차짜리 목표가 됐다**

T9-1에서 보스를 회차당 1회로 막았는데, 포획 천장(`SpeciesKills`)은 영구 데이터다.
골렘은 **회차당 1킬**이므로 천장 40에 닿으려면 40회차가 걸린다
(3% 굴림이라 기댓값은 약 23회차). `s_mon_stone`은 사실상 장기 목표가 됐다.
의도라면 그대로, 아니라면 보스 외에 골렘이 나오는 상시 방이 필요하다.

**시트 v0.2에 반영할 것** (T9-4): 자동 공격의 계수 스탯을 고정으로 둘지(INT 빌드 성립
여부가 여기서 갈린다) / 액티브 쿨다운 대 자동 공격 주기의 비중 / 컬렉션 종 수 / 골렘 획득 경로.
**DEF 피격 감쇄는 결정 항목이 아니라 구현 항목**이다 (기획서 §4.7에 이미 정의됨).
