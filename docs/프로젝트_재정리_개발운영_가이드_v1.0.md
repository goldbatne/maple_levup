## 1. 방향 재정리 — 무엇이 바뀌었나

### 1.1 최종 방향 (확정)

> **성장할수록 세계가 열리는, 방(房) 단위 탑다운 탐험 성장 RPG.**
> 피처폰 RPG(영웅서기·이카루스 전기)의 '구조적 감성'을 메이플 IP로 재해석한다.

네 기둥이 한 방향을 가리킨다:
- **장르**: 탑다운 탐험 성장 RPG
- **코어**: 성장(스킬 수집·레벨업)이 곧 '갈 수 있는 세계의 확장'
- **형태**: 방 단위 구역 돌파 (연속 오픈월드 아님)
- **미학**: 피처폰 RPG의 구조적 감성 (방 이동 / 압축된 밀도 / 단순한 전투)

### 1.2 살아남은 것 (기존 설계에서 유지)
- 환생 시스템 — 단, **성격 변경**: "리셋으로 더 강해짐"이 아니라 **"더 깊은 세계를 여는 열쇠"**
- 몬스터/직업 스킬 수집 + 제한된 슬롯 경제
- 스킬 컬렉션 → 스탯·고유 패시브 해금 (마일스톤 보상)
- 인플레이션 성장의 손맛
- 4스탯(ATK/INT/DEF/LUK), 비율식 데미지 공식, LUK 포획 스탯
- 데이터 구조 원칙(단일 테이블 + source + scaling_stat + schema_version)
- 솔로 플레이, 모바일 짬짬이, 자동공격+액티브 2~3개

### 1.3 폐기·전환된 것
| 기존 (v0.2) | 전환 후 | 이유 |
|---|---|---|
| 탐험 = 그라인딩의 '양념' | 탐험 = **코어** | 유저의 진짜 욕망이 '세계 모험'이었음 |
| 그라인딩이 코어 | 성장은 탐험을 굴리는 **엔진** | 코어/엔진 위계 역전 |
| "같은 맵 재사용으로 콘텐츠 절약" | **방 단위 + 성장 게이팅**으로 재방문 | 메트로배니아식 재해석 |
| 연속 스크롤 맵 | **방(화면) 단위 이동** | 피처폰 구조 + 1인 개발 통제성 |
| Re:END 장르(환생 그라인딩) | 탐험 성장 RPG | 출발 레퍼런스였을 뿐, 코어가 달라짐 |

### 1.4 새로 선 설계 원칙 (방 단위 구조)
1. **방 = 기본 공간 단위.** 화면 하나 = 하나의 방, 가장자리로 나가면 다음 방 전환.
   - 이점: 독립 제작·테스트 용이, 게이팅 자연스러움, 카메라/이동 코드 단순화.
2. **한 방에 목적 하나.** 사냥방 / 수수께끼방(스킬로 여는) / 보스방 / 상점방 / 발견방.
   죽은 공간 원천 봉쇄.
3. **단순하지만 리듬 있는 전투.** 자동공격 + 액티브 2~3개. 슬롯 제한 = "그 시절 버튼 부족"의 미학적 재현.
4. **스킬의 이중 역할**:
   - **열쇠 스킬** (소수·액티브): 이동·환경 상호작용 → 방/구역을 여는 능력
   - **컬렉션 스킬** (다수): 수집량이 임계(서로 다른 종류 N개)에 도달 시 **패시브 해금**.
     보상은 수치 뻥튀기(X) 아니라 **플레이 감각을 바꾸는 질적 변화**(O).
5. **방 배치 리듬**: 사냥방만 연속 배치 금지. 몇 방마다 다른 종류를 끼워 단조로움 방지.

### 1.5 리스크 (새 방향 고유)
- **맵/게이트 설계 밀도**: 그라인딩보다 공간 설계 난이도 높음. 어디를 잠그고 어떤 순서로 여는지가 게임의 질.
- **방 단조로움**: §1.4-5의 리듬 배치로 대응.
- **첫 목표는 여전히 수직 슬라이스**: 방 3~5개로 "성장→문 열림→새 방" 루프가 재밌는지부터 검증.

### 1.6 신청서 제출본 (기록)
- 장르: 탑다운 탐험 성장 RPG
- Core Loop: 몬스터·직업 스킬 수집 성장 → 제한 슬롯으로 지역 클리어 → 컬렉션(스탯·패시브) 해금
- 컨셉: 성장해야 열리는 구역 돌파 + 슬롯 제한이 만드는 "무엇을 들고 갈까" 선택
- (AI 활용은 신청서 별도 항목에서 다룸 — 본 3항목엔 미포함, 의도된 것)

## 2. 멀티 AI 개발 워크플로우

### 2.1 역할 고정 (절대 원칙)
| 주체 | 고정 역할 | 담당 |
|---|---|---|
| **코드 생성 AI** (A) | "짜는 놈" | 초안 코드 생성, 리팩터, 반복 작업 |
| **검증 AI** (나, B) | "의심하는 놈" | 설계 정합성 검증, 버그·구조 위반 탐지 |
| **단풍/RAG** (에디터 내) | "문법 확인" | mLua API 실존 확인, 에디터 특유 동작 |
| **본인** | "결정하는 놈" | 실행·판단·최종 결정 (AI 출력의 채택 여부) |

역할이 흔들리면 검증이 무의미해진다. A에게 검증을 겸하게 하지 말 것 — 자기 코드를 자기가 검증하면 못 잡는다.

### 2.2 표준 작업 사이클
```
1. B(나)에게 설계·의사코드 요청  → 태스크 목표 + 데이터 구조 전달
2. A에게 의사코드 → mLua 코드 생성 의뢰
3. 단풍에게 A의 코드 중 API 부분 실존 확인
4. VS Code에 반영 → 직접 실행 테스트
5. 안 되면: 에러+코드+의도를 B에게 검증 의뢰
6. 되면: 깃 커밋 (§3)
```

### 2.3 검증 요청 템플릿 (B=나에게 붙여넣기용)
> 나는 세션 간 기억이 없다. 매 검증 요청에 아래를 통째로 줄 것.

```
[태스크] 작업분해표 T번호 / 무엇을 만드는 코드인지 한 줄
[의도] 이 코드가 해야 하는 동작
[실행공간] 서버 / 클라이언트 / 둘 다
[관련 데이터 구조] 이 코드가 건드리는 테이블·필드
[코드] (A가 생성한 mLua 전문)
[증상] (있다면) 에러 메시지 or 예상과 다른 동작
[질문] 무엇을 봐주길 원하는지 (버그? 구조 위반? 최적화?)
```

### 2.4 B의 검증 체크리스트 (내가 볼 것)
검증은 "돌아가냐"가 아니라 "설계에 맞냐"까지 본다:
- [ ] **구조 정합**: 데이터가 단일 테이블 + source/scaling_stat 원칙을 지키나
- [ ] **저장 안전**: 영구 데이터(컬렉션)와 회차 데이터(레벨) 분리, schema_version 존재
- [ ] **서버 권한**: 데미지·스탯·포획 판정이 서버에서 도나 (클라 계산은 치트 구멍)
- [ ] **원자성**: 환생 등 다단계 변경이 중간 종료에도 반쪽 상태 안 남나
- [ ] **방 단위 정합**: 방 전환·게이팅 로직이 §1.4 원칙과 충돌 안 하나
- [ ] **수치 일치**: 밸런스 시트 값과 코드 상수가 같나 (하드코딩된 매직넘버 경계)

### 2.5 함정 (오답노트)
- A가 존재하지 않는 API를 그럴듯하게 지어냄 → 단풍/자동완성으로 실존 확인 필수
- A 코드가 "실행은 되는데 우리 구조를 어김" → B 체크리스트로 잡기
- 한 문제에 2시간 이상 → 멈추고 (코드+에러+의도) 묶어서 B에게
- 단풍 재질문 무한루프 → mLua 개념 선행 학습이 예방책

## 3. 깃 관리 전략

### 3.1 전제 사실 (✅ 2026-08-04 실측 확인)
- 메월드에 **LocalWorkspace + VS Code 연동** 기능 존재.
- 활성화: `File - Setting - 만들기 - LocalWorkspace`.
- 연동 시 **스크립트가 로컬 텍스트 파일로 빠지고**, 에디터 내 항목은 **읽기 전용**으로 전환
  (= VS Code가 스크립트 편집의 단일 창구가 됨).
- ✅ **확정**: 스크립트만이 아니라 **맵·UI·모델까지 전부 텍스트(JSON)로 빠진다.**
  **LocalWorkspace 폴더 = 프로젝트 루트 자체** (별도 하위 폴더 없음).

| 폴더 | 내용 | 깃 |
|---|---|---|
| `RootDesk/MyDesk/` | `.mlua` + **`.codeblock`(짝, 필수)**, `.stateset`, `.tileset` | 커밋 |
| `map/` | `.map` (JSON) | 커밋 |
| `ui/` | `.ui` (JSON) | 커밋 |
| `Global/` | `.model`, `.config`, `.gamelogic`, `.logic` | 커밋 |
| `Environment/NativeScripts/` | `.d.mlua` API 정의 (읽기 전용). 엔진 CoreVersion 고정용 | 커밋 |
| `.mswai/` | mLua LSP 런타임 + node_modules (약 9MB, 자동 재설치) | **제외** |

- ⚠️ `.model` / `.ui` / `.map`은 **빌더 경유 편집만 허용** (직접 JSON 편집은 차단됨).
  깃 diff·되돌리기에는 영향 없고, **편집 경로만** 제약된다.
- ⚠️ `.codeblock`은 자동 생성 메타데이터지만 **깃에서 빼면 안 된다** — 빠지면 스크립트가 등록되지 않는다.
  (내용을 손으로 고치지 말 것 / 커밋은 할 것)

### 3.2 권장 구조: ~~하이브리드~~ → **전 자산 표준 깃** (§3.1 확정에 따라 개정)
| 대상 | 관리 방식 |
|---|---|
| **mLua 스크립트** | 표준 깃 — 파일 단위 커밋·diff·브랜치. 핵심 자산. |
| **맵/모델/UI** | ~~스냅샷 백업~~ → **표준 깃**. 전부 JSON 텍스트라 diff가 읽힌다. 편집만 빌더 경유. |
| **밸런스 시트·기획서·문서** | 깃에 같이 넣는다. `.md`는 diff 가능, `.xlsx`는 바이너리 취급. |
| **비밀정보 / 툴링 캐시** | **제외**. `.mcp.json`(인증 토큰), `.mswai/`, `.claude/skills·hooks/` |

문서 3개가 서로 다른 값을 가리켰다:

| 출처 | 내용 |
|---|---|
| 기획서 §4.5 | **"한 랜드마크에 한 축만."** |
| 밸런스시트 `랜드마크 사다리` | Lv30 = 첫 환생 가능 / Lv55 = 직업2 / Lv70 = 슬롯+1 |
| 작업지시서 T7 | **Lv30 환생 → 직업2 + 몬스터 슬롯 +1 + 신규 구역** (한 랜드마크에 3축) |

**→ T7 압축안 채택.** 8주 안에 슬롯 확장 2축(보스=T6 1→2, 환생=T7 2→3)을 모두 체감시키는 것이
슬라이스의 검증 목표이므로, **Lv30 랜드마크에 한해 3축 동시 지급**한다.

단, **이는 슬라이스 한정 예외이지 본편 규칙이 아니다.**
- 본편 기준은 밸런스시트 `랜드마크 사다리`(Lv30/55/70/85/100…)이며 §4.5 "한 축만"이 유지된다.
- T0의 `LandmarkTable`은 **슬라이스 값으로 채우되, 본편 사다리로 교체 가능한 데이터 구조**로 만든다.
- T9 검증 후 본편 사다리로 되돌린다.
