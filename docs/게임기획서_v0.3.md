---

## 1. 게임의 정의

> **성장할수록 세계가 열리는, 방(房) 단위 탑다운 탐험 성장 RPG.**

### 1.1 코어와 엔진의 분업 (가장 중요한 원칙)

| 층위 | 정체성 | 레퍼런스 | 역할 |
|---|---|---|---|
| **코어** (왜 하는가) | 세계를 한 방씩 헤쳐나가는 맛 | 영웅서기·이카루스 전기 | 플레이의 목적 |
| **엔진** (무엇으로 굴리나) | 숫자가 오르는 성장의 손맛 | Re:END | 플레이의 동력 |

**한 문장**: *성장의 보상이 숫자가 아니라 새로운 땅이다.*

> **모든 기능 판단의 리트머스**: "이건 코어(탐험)를 강화하나, 엔진(성장)을 강화하나?"
> 둘 다 아니면 넣지 않는다.

### 1.2 재현하려는 것 — 피처폰 RPG의 '구조적 감성'
비주얼·서사가 아니라 **구조**를 재현한다. 이는 1인 개발이 통제 가능한 유일한 영역이자,
제약을 미학으로 전환하는 프레임이다. ("작게 만든다"가 아니라 "그 시절 구조를 재현한다")

- 방(화면) 단위 이동
- 압축된 밀도 (군더더기 없음)
- 단순하지만 리듬 있는 전투

### 1.3 차별점
메월드 상위권은 대부분 "본가 메이플 감성" 또는 "환생 그라인딩"을 판다.
**피처폰 RPG 구조 × 메이플 IP × 성장 게이팅** 조합은 확인된 범위에서 공백.
(단, 환생·직업·스킬수집 각 요소는 이미 여러 월드에 존재 — 조합과 완성도로 승부)

## 2. 코어 루프

```
방을 탐험한다 → 몬스터를 잡아 성장하고 스킬을 얻는다
      ↑                              ↓
  새 구역이 열린다  ←  잠긴 문의 조건을 충족한다
```

- 성장이 곧 '갈 수 있는 세계의 확장'으로 직결된다.
- 환생은 리셋이 아니라 **더 깊은 세계를 여는 열쇠**.

---

## 3. 공간 설계 — 방 단위 구조

### 3.1 기본 원칙
1. **방 = 기본 공간 단위.** 화면 하나 = 하나의 방. 가장자리로 나가면 다음 방으로 전환.
   - 이점: 독립 제작·테스트, 게이팅의 자연스러움, 카메라/이동 코드 단순화
2. **한 방에 목적 하나.** 죽은 공간 원천 봉쇄.
   - 방 유형: 사냥방 / 게이트방(조건부 통과) / 보스방 / 상점·거점방 / 발견방(숨김 요소)
3. **방 배치 리듬.** 사냥방 연속 배치 금지. 몇 방마다 다른 유형을 끼워 단조로움 방지.
4. **잠긴 문은 보여준다.** 못 가는 곳이 보여야 "돌아오고 싶은" 동기가 생긴다.

### 3.2 게이트 3종 (코어와 엔진을 잇는 접착제)

| 게이트 | 조건 | 담당 축 |
|---|---|---|
| **수치 게이트** | 공격력/레벨 X 이상이어야 돌파 | 엔진(Re:END식 성장) |
| **열쇠 게이트** | 특정 스킬·아이템 보유 시 개방 | 코어(영웅서기식 발견) |
| **환생 게이트** | 환생해야 열리는 구역 | 회차 루프 ↔ 세계 확장 |

**설계 규칙**: 수치 게이트를 기본 골격으로 깔아야 그라인딩이 탐험으로 직결된다.
열쇠 게이트만 쓰면 성장과 게이팅이 분리되어 두 감성이 따로 논다.

## 4. 시스템 설계

### 4.1 스킬 — 이중 역할
- **열쇠 스킬** (소수·액티브): 이동·환경 상호작용. 문을 여는 능력. 갯수가 적어 밸런스 통제 용이.
- **컬렉션 스킬** (다수): 수집 대상. 전투에 사용.
- 스킬마다 **계수 스탯**(ATK계/INT계) 지정 → 스탯 분배가 "직업 스킬 vs 주력 몬스터 스킬"의 선택이 됨.

### 4.2 스킬 컬렉션 → 패시브 해금
- **서로 다른 종류 N개** 수집 시 패시브 해금 (개수가 아닌 종류 기준 — 다양한 사냥 유도).
- 패시브 보상은 **수치 뻥튀기가 아니라 질적 변화**:
  - 나쁜 예: 공격력 +2% / 좋은 예: 처치 시 확률로 쿨 초기화, 이동 중 체력 회복
- 도감 UI와 직결. 수집 진행도가 곧 다음 해금까지의 목표.

### 4.3 슬롯 경제 (확정)

**구조: 직업 슬롯(고정) + 몬스터 슬롯(확장형)**

| 슬롯 | 개수 | 성격 |
|---|---|---|
| **직업 스킬 슬롯** | 고정 (직업 선택 시 자동 장착) | 항상 사용 가능. **직업을 선택하는 이유** |
| **몬스터 스킬 슬롯** | **시작 1개 → 확장** | 매번 "무엇을 들고 갈까"의 선택 대상 |

- **동시 사용 액티브 = 직업 스킬 + 몬스터 슬롯.** 시작 시점에도 최소 2개는 사용 가능
  (몬스터 슬롯만 1개라 초반이 밋밋해지는 문제를 직업 슬롯이 방어).
- **몬스터 슬롯 확장 조건 (2축)**:
  1. **보스 클리어** — 공간 진행 축
  2. **환생 횟수** — 회차 진행 축

  두 축이 서로 보완: 한쪽만 파도 진전, 둘 다 하면 더 빠름.

- **슬라이스 확장 사다리**: 시작 1 → 첫 보스 클리어 2 → 첫 환생 3
  (8주 안에 확장을 두 번 체감. 두 축이 각각 한 번씩 작동하는지 검증)
- 슬롯 상한은 3 근처 — 모바일 조작 + 피처폰 감성의 이중 근거.
- **몬스터 슬롯 1개 제약이 곧 재미**: 하나뿐이라 "이 구역엔 어떤 스킬을 들고 갈까"가
  매번 실제 고민이 된다. 슬롯이 많으면 이 긴장이 사라진다.
- 메타 수렴 방지: ① 구역마다 다른 환경/약점 ② 강한 조합엔 비용 ③ 수집 완성 자체를 동기로.

### 4.4 직업 — 회차별 육성
- 환생 시 직업 선택, 회차 단위 독립 육성.
- **고유 직업 스킬은 전용 슬롯에 항상 장착되어 사용 가능** (§4.3).
  직업마다 다른 특수 효과를 부여 — 이것이 **직업을 선택하는 이유**.
  직업 스킬이 몬스터 슬롯을 잠식하지 않으므로, 직업 정체성이 항상 유지된다.
- 직업 해금은 랜드마크 사다리에 배치.
- **링크스킬식 계승**: 직업 마스터 시 스킬 1개를 타 직업 회차에 계승.

### 4.5 환생
- 리셋: 레벨·스탯 분배 / 유지: 스킬 컬렉션, 랜드마크 기록, 환생 횟수, 최고 도달 레벨
- **도달 레벨 랜드마크**: 그 레벨에서 *환생해야* 보상 획득 (환생 버튼이 보상 순간)
- 보상 종류: 캡 확장 / 레벨당 스탯 티어 상승 / 직업 해금 / **몬스터 슬롯 확장**(§4.3 2축 중 하나) / **구역 개방**
- **한 랜드마크에 한 축만.**
  - ⚠️ **수직 슬라이스 한정 예외 (승인 2026-08-04)**: 8주 안에 슬롯 확장 2축을 모두 체감시키기
    위해, 슬라이스의 **Lv30 랜드마크만 3축 동시 지급**한다 — 직업2 해금 + 몬스터 슬롯 +1(2→3)
    + 신규 구역 개방. 작업지시서 T7 기준.
  - 이는 **검증용 압축이지 본편 규칙이 아니다.** 밸런스시트 `랜드마크 사다리`(Lv30/55/70…)가
    본편 기준이며, T9 검증 후 본편 사다리로 되돌린다.
- 문패 UI: 캡 도달 전부터 "다음 환생 시: OO" 사전 노출.

### 4.6 전투 (v0.2에서 유지 — 검증 완료)
```
데미지 = 스킬계수 × ATK² / (ATK + DEF)     [기준 계수 1.2]
```
- 비율식 뼈대 + 곱셈 겹 상한 3~4개.
- 자동 공격 + 액티브 탭. 단순하되 리듬 있게.

### 4.7 스탯 4종 (v0.2에서 유지)
| 스탯 | 역할 |
|---|---|
| ATK / INT | 물리계·마법계 스킬 계수 |
| DEF | 생존 (통합 방어) |
| LUK | 포획 확률·드랍률 — 회차 목적을 정의하는 시그니처 스탯 |

- 레벨당 기본 5P, 랜드마크 티어로 증가(5→6→7).

### 4.8 포획
- 처치 시 자동 판정 (추가 조작 없음).
- 확률 = 3% + LUK×0.1%p, **종별 40킬 천장** (빈손 방지).
- 성공 시 스킬 획득 → 컬렉션 추가. 중복은 강화 카운트.

## 6. 개발 방침

### 6.1 AI 협업 (학습 최소화)
- **문법·API는 학습하지 않는다.** AI에게 맡긴다.
- 대신 **판단 기준 2개**만 반나절 확인: ①서버/클라이언트 실행공간 ②엔티티·컴포넌트 구조
  - 이유: "AI 코드가 맞는지 틀린지" 판단 못 하면 무한 재질문에 빠짐
- **지시서에 판단 기준을 내장**한다 (작업분해표 v2.0의 각 프롬프트에 규칙 명시)

### 6.2 데이터 구조 원칙
- 스킬: 단일 테이블 + `source`(job/monster) + `scaling_stat`(ATK/INT) + `slot_type`
- 세이브: `schema_version` 필수. **영구 데이터(컬렉션)와 회차 데이터(레벨) 분리**
- 방/게이트: 데이터로 정의 (방 추가가 코드 수정 없이 가능하게)

**구현 확정 (T0, 2026-08-04)**
- 정적 데이터는 **UserDataSet(`.userdataset` + `.csv`)** — `RootDesk/MyDesk/GameData/`
  6종: `GameBalance` / `SkillTable` / `MonsterTable` / `RoomTable` / `JobTable` / `LandmarkTable`
  → **CSV만 교체하면 코드 수정 없이 밸런스 패치.** T9 시트 역기입과 직결.
- 조회는 **`GameData` @Logic 한 곳만 경유**. `_DataService` 직접 호출 금지.
  string→number 변환, `conn_*` 4컬럼 접기, 파이프(`|`) 배열 파싱을 여기 가둔다.
  → 저장 방식을 바꿔도 이 파일만 고치면 된다.
- 세이브는 `SaveRunData`(회차) / `SavePermanentData`(영구) **@Struct 2개**로 분리.
  직렬화 시 `Run` / `Perm` 최상위 키로 갈라지므로 T7 환생은 회차 키만 초기화한다.
- CSV는 중첩을 못 담는다 → 컬럼 평탄화가 전제. 새 필드는 컬럼 추가로 대응.

### 6.3 버전 관리
- **LocalWorkspace = 프로젝트 루트 자체** (별도 하위 폴더 없음). 2026-08-04 확인.
- **스크립트뿐 아니라 맵·UI·모델·스테이트셋·타일셋까지 전부 텍스트(JSON)로 빠진다.**
  → 하이브리드(스크립트만 깃 + 나머지 스냅샷) 불필요. **전 자산 표준 깃 diff 관리.**
- 단, `.model` / `.ui` / `.map`은 **빌더 경유 편집만 허용**된다 (직접 JSON 편집 차단됨).
  깃 관리에는 영향 없고 편집 경로만 제약.
- 깃은 **협업이 아니라 되돌리기용**. "작동하는 상태마다 커밋" 그것만.
- 커밋·푸시는 Claude Code에 위임, 인증만 직접.
